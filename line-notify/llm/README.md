# llm/：LLM 轉譯（本地模型優先）

車外狀態機決定「要通知」之後，把 notice（結構化的事實）寫成給家屬的句子。
**LLM 只負責寫句子，不決定要不要通知**（那是狀態機的職責，維持規則式、可測試）。

```
車外狀態機 ──► notice ──► LLMFormatter ──► LINE
                             │  背景執行緒：本地模型（MLX，啟動時載入並預熱，只載入一次）
                             └─ 逾時／失敗／沒通過檢查 → machine.format_message()（固定模板）
```

任務說明：`docs/tasks/04-llm.md`。`state_machine/`、`transport/` 沒有任何修改。

| 檔案 | 內容 |
|---|---|
| `formatter.py` | `LLMFormatter`（訊息產生器）、`background_output()`（不阻塞狀態機的背景輸出） |
| `backends.py` | 後端：`template`、`local`（MLX）、`cloud`（預留） |
| `prompt.py` | 提示詞、範例、輸出檢查規則 |
| `eval.py` | 模板與 LLM 的比較評測 |
| `eval-results.md` | 評測結果全文（`eval.py` 產生，含每則並排輸出） |
| `../tests/test_llm_formatter.py` | 測試（假的後端，不載入模型、不需網路） |

## 一、安裝與設定

### 需要什麼

- 本地模型：Apple Silicon 的 macOS（M1 以上）。其他平台會自動退回模板，整條線照常運作
- `mlx-lm`：**不寫進 `pyproject.toml`**（專案要相容 Python 3.6 的車上環境，mlx-lm 需要 3.8+ 且只能在 Mac 上跑），
  改用 `uv run --with mlx-lm` 臨時帶入，不需要 pip
- 模型檔：第一次執行會自動從 Hugging Face 下載到 `~/.cache/huggingface/`（約 1.6GB），之後離線可用。
  想先下載：`hf download mlx-community/Qwen2.5-3B-Instruct-4bit`

### 用法

```python
import sys
sys.path.insert(0, "state_machine"); sys.path.insert(0, "llm")
from machine import StateMachine, line_output
from formatter import LLMFormatter, background_output

fmt = LLMFormatter()          # 立刻返回；模型在背景載入並預熱（約 12 秒），這段期間的通知先用模板

# 接法一：直接當 formatter。有通知的那一拍最多卡住 timeout 秒（預設 3 秒）
sm = StateMachine(outputs=[line_output(dry_run=True, formatter=fmt)])

# 接法二（建議）：交給背景輸出。狀態機那一拍立刻返回，產生文字與送 LINE 在背景進行
sm = StateMachine(outputs=[background_output(line_output(dry_run=True, formatter=fmt), formatter=fmt)])
```

執行（要用本地模型時帶上 mlx-lm）：

```bash
uv run --no-project --with mlx-lm python 你的程式.py
```

### 設定

環境變數或專案根目錄 `.env`（已設定的環境變數優先），也可以直接傳參數給 `LLMFormatter(...)`：

| 設定 | 預設 | 說明 |
|---|---|---|
| `JETBOT_LLM_BACKEND` | `local` | `template`／`local`／`cloud` |
| `JETBOT_LLM_TIMEOUT` | `3` | 逾時秒數，超過就用模板 |
| `JETBOT_LLM_MODEL` | `mlx-community/Qwen2.5-3B-Instruct-4bit` | 本地模型名稱 |

```bash
uv run python tests/test_llm_formatter.py
```


## 二、設計重點

### 1. 絕不拖垮通報

| 要求 | 做法 |
|---|---|
| 逾時上限 3 秒 | 呼叫端只等到 `timeout` 為止，超過就回傳模板 |
| 不阻塞判斷迴圈 | 模型的載入與產生都在**同一條背景執行緒**（MLX 的運算串流綁定執行緒）。另外提供 `background_output()`：狀態機那一拍只把通知排進佇列就返回，連等待的時間都不佔用 |
| 同一則只送一次 | 逾時後把那次工作標記為取消：模型在下一個 token 就停下，就算停不下來，結果也不會再被使用，因為模板已經回傳 |
| 排隊的通知不各自等滿 | 用 `background_output(..., formatter=fmt)` 時，逾時從**排入背景的時間**起算。同一時間多則通知，後面的不會每則再等 3 秒 |
| 例外全部吞掉 | `LLMFormatter.__call__` 不會往外拋；連模板都失敗時（notice 格式錯）仍給一則最基本的訊息 |

### 2. 什麼情況都有訊息可送

以下都自動退回模板，每種原因**只提示一次**（`[LLM] ...`）；原因記在 `fmt.last["reason"]`、`fmt.records`：

| 情況 | 原因代號 |
|---|---|
| 沒安裝 `mlx-lm`、不是 Apple Silicon、模型載入失敗、`cloud` 未實作、後端名稱打錯 | `unavailable` |
| 模型還在載入（啟動後約 12 秒內） | `loading` |
| 產生逾時 | `timeout` |
| 上一則逾時的產生到逾時上限都還沒停下 | `busy` |
| 回應為空 | `empty` |
| 沒通過輸出檢查 | `check`（沒過哪幾條記在 `failed_rules`） |
| 其他例外 | `error` |

### 3. 輸出檢查（`prompt.check_output`）

| 代號 | 規則 | 怎麼檢查 |
|---|---|---|
| `traditional` | 繁體中文、台灣用語 | 約 150 個常見簡體字（只收台灣不會出現的字）＋大陸用語清單（信息、視頻、網絡……） |
| `length` | 本文 ≤ 120 字 | 不含開頭、空白、換行 |
| `no_fields` | 沒有欄位名稱或 JSON | `has_target` 這類底線名稱、notice／車上欄位與代號、`{}[]"` 等符號 |
| `no_english` | 沒有英文或提示詞殘留 | 本文出現連續兩個以上英文字母、或「事實：」「<\|」等標記 |
| `numbers` | **數值必須來自 notice** | 取出本文所有數字（含「三十秒」這類中文數字），每一個都要對得上 notice：持續時間（`format_duration` 的寫法或精確秒數，含 `others`）、距離（小數一位、兩位或公分）、被擋機率、時刻。**`distance_m` 為 null 時寫出任何距離都不會過** |
| `no_medical` | 不給醫療建議 | 送醫、就醫、急診、救護車、吃藥……，以及推測身體狀況（受傷、跌倒、昏倒） |
| `header` | 以 `【伴護機器人】HH:MM` 開頭 | 開頭由程式加上（模型只寫本文，模型自己寫的開頭會先去掉），檢查時間正確、只出現一次 |
| `consistent` | 提到的狀況與 notice 相符（**自行加的**） | notice 有的類別要提到（受護者／通過、擋、障礙／連線）；沒有失聯卻提到「連線」就不過 |

| `duration_semantics` | 持續時間不可寫成「多久以前」（**任務六加的**） | 本文出現「秒前」「分鐘前」「分半前」「小時前」就不過 |

`consistent` 是評測時發現的：模型把「找回受護者」寫成「連線恢復了」，其他規則都抓不到。
`duration_semantics` 是 2026-09-29 實際送出 LINE 時發現的：「約 7 秒前就被擋住了」「約 13 秒前就已經重新連上」，數字對但意思錯。

### 4. 提示詞

- 系統提示詞：角色（對家屬說話的伴護機器人）、語氣（平實、不誇張、不製造恐慌）、每條限制、「沒有的資訊就不要提」
- **範例 8 組**（事實 → 理想訊息），以 user／assistant 一問一答的形式放在系統提示詞之後。理想訊息取自 `machine.TEMPLATES`（任務六：Claude 產生、人工審核），涵蓋 alert／reminder／recovery、`others` 併入、有距離與無距離、卡住解除的兩種分支，以及 9/29 寫錯時間語意的兩種情況
- 系統提示詞寫明車子的實際行為（看不到受護者時停在原地等待、失聯時無法得知車子狀況），並禁止「約 N 秒前」的寫法
- 卡住解除多給一個事實 `following`（車子是否繼續跟隨），其餘仍不給 `car`
- 事實：以 `machine.notice_facts()` 為基礎整理成小模型好讀的樣子（見「自行選擇的做法」第 2 點）
- **提示詞快取**：系統提示詞＋範例（847 個 token）每次都一樣，預熱時先算好 KV 快取，之後每則只處理最後的事實。產生時間從**約 9 秒降到約 2 秒**，是能在 3 秒內完成的關鍵

## 三、比較結果

2026-09-24，M1 MacBook Air 8GB、macOS 15.7.4、mlx 0.32.2、mlx-lm 0.31.3。題目是 `transport/simulator.py` 的情境重播出的 16 則 notice，全文見 `eval-results.md`。

### 量測

| 項目 | 結果 |
|---|---|
| 模型 | `mlx-community/Qwen2.5-3B-Instruct-4bit`（Qwen2.5 3B Instruct，4-bit 量化） |
| 模型檔大小 | 1.74GB（`model.safetensors` 1,736,293,090 bytes；含 tokenizer 的快取資料夾 1.6GiB） |
| 模型載入 | 1.7～1.9 秒（檔案已在本機快取） |
| 預熱（含建立提示詞快取） | 8.7～11 秒 |
| 從建立 `LLMFormatter` 到可用 | 約 12 秒 |
| 每則產生耗時 | **中位數 1.8～1.9 秒、最大 2.8 秒**（兩次評測） |
| 載入後記憶體 | MLX 配置 1,774MB、高峰 2,396MB |
| 阻塞狀態機（接法一，直接當 formatter） | 有通知的拍：中位數 1.8 秒、最大 2.6～3.0 秒（上限就是 timeout）；其他拍 < 0.1 ms |
| 阻塞狀態機（接法二，`background_output`） | **有通知的拍 < 0.1 ms**；其他拍 < 0.1 ms |
| 背景完成耗時（同一瞬間連續 4 則） | 1.8、3.0、3.0、3.0 秒：第一則用 LLM，後三則在排隊中用完 3 秒預算，改用模板 |

> 阻塞時間是在 `eval.py` 裡重播同一段情境（卡住 → 解除 → 失聯 → 恢復），用實際時鐘量每拍 `tick()` 的耗時。
> 重播用假時鐘，4 則通知在一瞬間連續發生，比實際嚴苛（實際上通知之間隔好幾秒）。

### 退回率與檢查

| 項目 | 本地模型 |
|---|---|
| 正式設定（逾時 3 秒）採用 LLM | **16 / 16**（兩次評測都是） |
| 不限時間時各條檢查 | 9 條全部 16 / 16 通過（任務六後為 10 條，見下方） |

調整過程中被檢查擋下、改用模板的例子（證明檢查有用）：

| 情況 | 模型寫的 | 哪條擋下 |
|---|---|---|
| 測距讀不到（null）卻寫出距離 | 「障礙物約 0.4 公尺處」（抄範例的數字） | `numbers` |
| 「找回受護者」寫成連線恢復 | 「和機器人的連線恢復了，已經約 3 分鐘了」 | `consistent` |
| 前幾版產生超過 3 秒 | — | `timeout` |

### 並排範例

| 情況 | 模板 | 本地模型 |
|---|---|---|
| 卡住 | 車子判定前方無法通過，已停在原地。／目前距離前方障礙約 1.2 公尺。 | 前方無法通過，距離約 1.2 公尺。車子停在原地等待。 |
| 看不到受護者（提醒） | 車子仍然看不到受護者，已持續約 5 分鐘。 | 車子到現在還是看不到受護者，已經約 5 分鐘了。 |
| 找回受護者 | 車子已重新找到受護者，恢復跟隨（中斷約 11 分鐘）。 | 車子已經重新找到受護者，恢復跟隨了，剛才大約 11 分鐘沒看到人。 |
| 卡住＋連線恢復 | 車子判定前方無法通過，已停在原地。／目前距離前方障礙約 0.3 公尺。／另外，連線已恢復。 | 前方被擋住了，距離約 0.3 公尺。另外，和機器人的連線中斷了約 13 秒，已經恢復。 |

### 品質觀察（檢查抓不到的）

- **時間的語意偶爾錯**：「約 2 分鐘前就被擋住了」（應為「停了約 2 分鐘」）、「約 13 秒前就已經重新連上」（應為「中斷約 13 秒」）。數字對，意思不對，自動檢查抓不到 → **任務六已處理，見下一節**
- 句子大多是範例的改寫，變化不大；「同一拍兩件事」能寫成一段完整的話，比模板自然
- 結論：**整條線跑得通**，本地小模型可以在 3 秒內產生、全部通過檢查；但語意精確度不如模板。若要當正式展示，建議升級（見第五節）或維持模板

## 四、自行選擇的做法

1. **模型**：`mlx-community/Qwen2.5-3B-Instruct-4bit`（2026-09-24 於 Hugging Face 確認存在與大小）。沒選更新的 Qwen3.5-4B：超過 40 億參數上限的邊緣，且是會先輸出思考過程的模型，在 3 秒內寫完一則的可能性低
   > **更正（2026-10-01，10-11 修訂）**：Qwen3.5 小模型（0.8B～9B）的思考模式預設開啟，但可用 chat template 參數 `enable_thinking=False` 關閉，後一個理由不成立。任務七重新評估 4B 與 9B
2. **給模型的事實不是 `notice_facts()` 原封不動**：評測發現原樣給會出錯，改成（`prompt.facts_for_prompt`）：
   - 拿掉 Unix 秒數（`time`、`since`、`car_ts`）：對模型沒意義，還可能被抄進訊息；時間由固定開頭寫
   - `duration_sec` 換成 `format_duration()` 的文字；不到 1 秒（剛發生）不給，避免寫出「已經約 0 秒」
   - 拿掉 `car`：模型在「卡住」時因 `has_target: false` 寫出「看不到受護者」
   - `readings` 只給模板也會寫的欄位（`machine.READING_TEMPLATES`，目前只有卡住時的距離）：模型曾在「看不到受護者」時寫出距離，家屬會誤以為是與受護者的距離
   - 提示詞變短，每則也快了約 0.5 秒
3. **開頭由程式加**：模型只寫本文，`【伴護機器人】HH:MM` 由程式加上，時間一定正確；模型自己寫的開頭會先去掉
4. **提示詞快取**（上面第二節第 4 點）：沒有它，每則要 8～10 秒，全部逾時
5. **貪婪解碼（temperature 0）**：同一則通知每次產生的文字相同，評測可重現
6. **新增 `consistent` 檢查**：任務沒要求，評測時發現需要
7. **`background_output()`**：任務要求「避免阻塞判斷迴圈」。只當 formatter 用時，那一拍最多卡 3 秒（期間快取仍在更新，但失聯判斷、其他通知會延後）；包一層背景輸出後阻塞 < 0.1 ms。代價：`notice["latency_sec"]` 只量到交給背景為止，真正送出的結果之後補進 `notice["outputs"]`（標「背景：」）
8. **忙碌時等待而不是立刻放棄**：上一則逾時的產生要到下一個 token 才會停（處理提示詞時停不下來，最多約 1 秒），下一則在逾時預算內等它讓出來
9. **`mlx-lm` 不加進 `pyproject.toml`**：用 `uv run --with mlx-lm`（理由見第一節）
10. **評測題目**：`simulator.SCENARIOS` 目前有 10 個情境（不是行前檔寫的 8 個），其中 5 個不會產生通知。另外補了兩個情境（11 分鐘看不到受護者，會有 reminder；測距讀不到時卡住），以及一則人工組出的「同一拍兩件事」，共 16 則

## 五、未來升級方向（本次不做）

本地小模型品質不夠時，可以換成雲端 API。**程式上只需要新增一個後端類別、改一個設定**：

1. 在 `backends.py` 的 `CloudBackend` 實作 `load()`（用官方 SDK 建立 client，金鑰從 `.env` 讀）與 `generate(messages, should_stop)`（`messages[0]` 是系統提示詞，其餘照送，回傳文字）。**照官方 SDK 寫，不要自己打 HTTP**
2. `.env` 加上金鑰（例如 `ANTHROPIC_API_KEY=...`），設定 `JETBOT_LLM_BACKEND=cloud`

逾時、輸出檢查、退回模板、背景輸出都在 `formatter.py`，**不用改**。`eval.py --backends local,cloud` 就能三種並排比較。

| 項目 | 說明 |
|---|---|
| 候選 | Anthropic Claude（Haiku 最便宜、Opus 品質最好）、Google Gemini |
| 費用 | 行前檔估算：每月 200 則、每則約 500 輸入＋100 輸出 token，Haiku 4.5 約 US$0.2／月、Opus 約 US$1／月。**尚未對照官方價目表查證** |
| 要準備什麼 | API 金鑰（放 `.env`，不可寫進程式）。**聊天版的訂閱不能用在 API，兩者分開計費** |
| 什麼時候該換 | 退回率偏高、訊息品質不足以展示、或報告書需要「本地 vs 雲端」的對照數據 |
| 雲端要注意 | 網路往返會吃掉逾時預算；手機熱點下的延遲未量測。提示詞快取的設計在雲端也有對應功能（固定前綴放前面即可） |

**混合策略**（可寫進報告）：平常用本地，**只有重要事件（卡住、失聯）才用雲端**產生較好的文字。
做法是再寫一個小的組合後端，依 notice 的 `category` 決定交給哪個後端；介面不變。

本地推論在報告書上也是優點：整條線包含語意轉譯都在邊緣端完成，不依賴雲端服務。
